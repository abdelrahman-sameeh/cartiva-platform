# نموذج الدفع والتسوية في Cartiva

يوضح هذا الملف ما يحدث حاليًا في الدفع الإلكتروني والدفع عند الاستلام، خصوصًا عندما يحتوي الطلب الواحد على منتجات من عدة بائعين.

## تركيب الطلب متعدد البائعين

- ينشئ العميل `Order` واحدًا.
- ينقسم الطلب إلى `SubOrder` مستقل لكل بائع.
- لكل `SubOrder` شحنة مستقلة ورقم تتبع مستقل.
- يحتفظ `Order` بإجمالي عملية العميل، بينما يحتفظ كل `SubOrder` بنصيب بائعه والخصم الخاص به.

## نموذج Stripe المستخدم

يستخدم المشروع نموذج Stripe Connect المعروف باسم **Separate Charges and Transfers**:

1. ينشئ Stripe Checkout عملية دفع واحدة على حساب المنصة لكل `Order`.
2. يتم ربط `PaymentIntent` بمجموعة تحويلات من خلال `transfer_group` مثل `ORDER_123`.
3. يؤكد Stripe الدفع عن طريق Webhook؛ الرجوع إلى صفحة النجاح وحده لا يجعل الطلب مدفوعًا.
4. ينشئ النظام سجل `SellerTransfer` لكل `SubOrder`، لكنه لا يحول المال للبائع قبل اكتمال طلبه الفرعي.
5. بعد اكتمال `SubOrder`، يرسل النظام صافي مستحق هذا البائع إلى حسابه المتصل في Stripe.

صافي تحويل البائع يحسب هكذا:

```text
نصيب البائع من تسوية Stripe
- نصيبه من رسوم Stripe
- عمولة المنصة
= صافي التحويل للبائع
```

يتم توزيع رسوم Stripe وفرق عملة التسوية نسبيًا على الطلبات الفرعية، مع حفظ الأرقام الفعلية بوحدة العملة الصغرى لتجنب أخطاء الكسور.

الأمر التالي يعيد محاولة التحويلات المعلقة أو الفاشلة:

```bash
php artisan stripe:retry-seller-transfers
```

ويعمل تلقائيًا كل دقيقة من Laravel Scheduler.

## الإلغاء والاسترداد في Stripe

- لا يتم تحويل مستحق البائع قبل اكتمال `SubOrder`، لذلك يمكن إلغاء الشحنة قبل التسليم دون استرداد المال من البائع.
- إذا كان الطلب مدفوعًا ثم أُلغي `SubOrder` قبل التسليم، ينشأ `Refund` جزئي بقيمة هذا الطلب الفرعي فقط.
- الاسترداد له `idempotency_key`، ولذلك إعادة المحاولة لا تنشئ استردادًا مكررًا.
- لو كان تحويل البائع قد تم بالفعل، يمنع النظام الإلغاء التلقائي لأن الحالة تحتاج Stripe Transfer Reversal ومراجعة تشغيلية.

معالجة الاستردادات المعلقة:

```bash
php artisan stripe:process-refunds
```

ويعمل هذا الأمر تلقائيًا كل دقيقة أيضًا.

## الدفع عند الاستلام عبر شركة الشحن

المزود الحالي `demo_shipping` تجريبي ولا يتصل بشركة حقيقية. لكنه يحاكي الدورة المطلوبة لكل `SubOrder`:

```text
created -> picked_up -> in_transit -> delivered
                                      |
                                      v
                         COD collected -> remitted -> seller paid
```

- `delivered`: شركة الشحن تؤكد التسليم وتحصيل المبلغ من العميل.
- `collected`: المبلغ أصبح مع شركة الشحن، وليس مع المنصة بعد.
- `remitted`: شركة الشحن حولت التحصيل إلى المنصة.
- `seller-paid`: المنصة سجلت صرف صافي مستحق البائع.
- `returned`: لم يتم التسليم؛ يعاد المخزون، يلغى `SubOrder`، يعاد حساب إجمالي الطلب، ويحرر استخدام الكوبون.

صافي مستحق بائع COD:

```text
المبلغ المحصل
- عمولة المنصة
- رسوم الشحن
- رسوم تحصيل COD
= صافي مستحق البائع
```

القيم التجريبية تضبط من `.env`:

```dotenv
PLATFORM_COMMISSION_BPS=500
DEMO_SHIPPING_FEE=0
DEMO_COD_COLLECTION_BPS=100
```

`500` نقطة أساس تعني 5%، و`100` نقطة أساس تعني 1%.

## تجربة شركة الشحن محليًا

احصل على رقم التتبع من صفحة طلب البائع، ثم نفذ الأحداث بالترتيب:

```bash
php artisan shipping:demo DEMO-1-XXXXXXXX picked-up
php artisan shipping:demo DEMO-1-XXXXXXXX in-transit
php artisan shipping:demo DEMO-1-XXXXXXXX delivered
php artisan shipping:demo DEMO-1-XXXXXXXX remitted
php artisan shipping:demo DEMO-1-XXXXXXXX seller-paid
```

ولتجربة شحنة فشل تسليمها:

```bash
php artisan shipping:demo DEMO-1-XXXXXXXX in-transit
php artisan shipping:demo DEMO-1-XXXXXXXX returned
```

الأحداث قابلة للتكرار بأمان؛ تكرار نفس الحدث لا يكرر التحصيل أو إعادة المخزون أو الاسترداد.

## نقطة مهمة قبل الإنتاج

عند اختيار شركة شحن حقيقية، يستبدل الأمر التجريبي بتكامل API وWebhook موقع بتوقيع سري. يجب مطابقة تقرير تحويل COD البنكي مع الشحنات قبل تغيير الحالة إلى `remitted`، وعدم اعتبار تأكيد التسليم وحده دليلًا على وصول المال للمنصة.
